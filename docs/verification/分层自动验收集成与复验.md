## 框架如何集成

入口仍是 `POST /api/runs` 选择已登记 `project_id`，不接受网页传入任意 Shell 或凭据。新增 `assessment-expanded-v1` 配置，以及专用 `assessment-v1` 编排适配器；旧两项规则方案保留。

执行顺序：冻结基线 → 核对用例 → L1 构建/静态检查与回归 → L2 临时数据库/接口 → L3 浏览器 → L4 恢复 → 环境清理 → 失败归纳 → OPA 判定。

- 来源：显式文件白名单、测试名称清单、来源文档、锁文件、编排资产摘要共同封存。依赖缓存必须与五份 package/lock 清单逐字节一致，否则阻断。
- 构建：使用固定本地镜像 ID，创建并核对本次专用标签；Dockerfile 最终阶段只复用依赖目录，然后复制本次源文件。避免旧镜像源代码覆盖新快照。
- 运行：临时 PostgreSQL 内部网络、合成账号和数据。Node、Python 和密钥扫描无外部网络；npm audit 单独容器仅挂载依赖清单，访问公共 npm registry。
- 成熟组件：Node Test Runner/JUnit、Python unittest、Playwright/axe-core、Gitleaks、npm audit、pg_dump/pg_restore、OPA。新增代码负责调度、归档、格式核验、关联和呈现。
- 证据：JUnit/JSON 原始字节、每次命令起止时间/退出码/日志、Playwright trace/截图、恢复数据指纹、门禁输入输出。
- 判定：检查原始报告清单/统计/状态与命令退出码、目标和基线绑定、构建镜像绑定。测试跳过、前置失败、未接入能力均不转换成通过。
- 生命周期：命令限时、标准输出/错误分别限制 4 MiB；最后按本次名称清理。服务中断后，下次启动按准确执行标签回收其容器和网络，不 prune 其他资源。
- 历史：报告格式版本与旧记录兼容；新编排变化会使旧记录标为不适用于当前输入，不改写旧记录的原始结果。

该实现仍是**一个真实项目的显式适配器**，不是任意仓库一键全验收。报告哈希与本地执行记录也不是第三方签名证明，不能证明对抗恶意执行者的来源真实性。
