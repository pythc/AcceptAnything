已与线程“你帮我找一下，是不是有一个可以把ChatGPT网页版的反带出来的这么一个开源项目。”沟通。对方实时模型目录HTTP200，提供无凭据交接：本机Chat2API，Chat Completions兼容接口，模型ID `gpt-6-thinking`，`reasoning_effort: high` 本地映射到网页 `extended`。这是该网关的兼容映射，不是官方API型号命名或等价性声明。

## 实现

- 连接通过被Git忽略的 `var/planner-connection.json` 持久保存；服务启动器每次读取同一文件路径。密钥直接从现有Chat2API本机配置中的 `LOCAL_API_KEY` 字段读取，不复制网页登录令牌，不写前端、方案、报告或代码包。
- 请求显式设置gpt-6-thinking、high、非流式JSON对象、临时会话、关闭自动续写；本地输出上限32768。首次联调使用600秒读取超时；发生超时后，后续配置调整为3900秒，覆盖网关3600秒总预算并留回传余量，不自动重试。客户端断开不保证上游生成已停止，因此超时后先按请求ID核对终态，再决定是否另发请求。
- 同一验收应用同时只允许一个模型方案请求；第二个请求在HTTP调用前拒绝。
- Chat2API配置若改为Pro/auto或其他强度，在发送前拒绝。收到响应后核验实际model=gpt-6-thinking、thinking_effort=extended、finish_reason=stop，再按既有严格方案Schema、独立原文引用和环境验证；不匹配、不完整或未知数据均不能变成可执行方案。
- 草稿及冻结方案保存请求/实际型号、强度、双端请求ID、耗时、结束原因及网关生成/重试预算计数；不保存隐藏分析或网页登录凭证。
- 页面显示“GPT-6 Thinking · High”；原结构化方案模式继续可用。模型生成仍需复核业务语义，再确认执行。

## 来源与边界

[OpenAI Docs reasoning指南](https://developers.openai.com/api/docs/guides/reasoning)说明Chat Completions使用reasoning_effort，推理模式与强度是不同参数。本地网页反代能力与型号映射以对方的实时交接、源码与本次响应为准。网关SSE先缓冲最终答案，本项目选择非流式；等待无数据不等于持续有效推理。网页登录状态、上游限额、传输及网关恢复可能导致失败，不能保证长期可用。JSON对象模式不等于严格Schema，必须由验收平台再次验证。
