## 1. 结果契约

新增 `acceptance/results.py`，提供 `acceptance-result-v1` 及严格的嵌套 Pydantic / JSON Schema。保留当前 OPA，结构校验先于门禁，不让模型生成最终放行结论。

| 对象 | 内容及判定原则 |
| --- | --- |
| execution | 排队、执行、结束、异常、取消、中断；分项状态与原始测试状态计数。执行结束不是通过。 |
| coverage | 所声明范围、已验证/未验证/事先排除的需求数量、结构阻断与覆盖原因。排除项不算通过。 |
| requirements | 原需求 ID、中文名称、文档来源、原文、用例 ID、处置与验证状态；不会用源码输出生成预期。 |
| observations | 检查、用例、报告内测试 ID、attempt、关联需求、实际状态和证据引用。 |
| findings | 使用有证据绑定的已有复核汇总；测试异常不能自动变成已确认缺陷。 |
| gate | 保留 recorded_decision，另给当前核验后的 decision；当前核验失效时不能沿用旧 allow。 |
| provenance | 源码/输入/执行器/策略摘要、证据引用和本次原件核验结果。没有采集的摘要留空。 |

原因采用稳定枚举：缺依据、环境未准备、平台未支持、用例契约问题、工具异常、模型设计未完成、中断/取消、缺报告、报告不完整、身份不一致、缺规则、证据不符等。只有已记录的结构化分类可用于归因，不靠英语报错或 `assert` 字样猜测缺陷。

新增安全检查包括：任务与冻结计划集合一致，任务/规则身份唯一，规则覆盖所选任务，完整报告和报告引用存在，规则处于可判定状态，模型声明的必验用例确有唯一有效结果。正常失败断言可以证明用例已执行，但仍由门禁规则决定拒绝；异常和跳过不能作为有效覆盖。

旧运行文件只读投影，保留原决定。新运行的 OPA 输入保存 contract_version / contract_blockers / contract_ready；策略原件继续封存。原策略的拒绝不会因今天的分类变化被反向改成通过。

接口：

- `GET /api/runs/{id}/result-contract`：重新核验后返回统一结果。
- `GET /api/result-contract/schema`：可用于集成的 JSON Schema。
- 主详情接口同时携带 `result_contract`，证据页可下载“核验结果 JSON”。该 JSON 是当前投影，和历史原件的下载入口分别保留。

覆盖分母只代表已冻结、可追溯的验收义务。没有独立需求不能宣称覆盖项目全部业务；本批未新增未知需求的推断能力。

## 2. 反例和故障验证

新增 `tests/test_result_contract.py`、`test_history_index.py`、`test_job_recovery.py`、`test_proof_readers.py`，并保留全部原测试。

结果反例覆盖六类执行状态 × 报告完整/不完整 × 三类规则状态 × 原件有效/失效的 72 种组合；另测空任务、重复/缺少身份、冻结清单不一致、缺规则/报告/引用、未知测试状态、跳过、错误、错误的 allow、缺失/重复模型用例和篡改原件。计数不接受负数，原因不接受未知枚举。

恢复验证包括：

- 入队写入前/后故障、重复投递、已领取但未启动、运行记录已启动但队列表尚未领取、终态已写但任务回执未写。
- 已取消但记录尚未同步、队列消息在领取前丢失、心跳所有权不符、旧数据库加字段迁移、超过旧 200 项界限的任务与事件分页。
- 单条 envelope 损坏、报告分片损坏、记录丢失；损坏的原文件保留，其他任务仍能继续。
- 容器枚举、容器删除、网络删除、卷删除故障；清理失败保持恢复待办，后续可以继续清理，不能伪装终态。
- 在模型等待、容器启动阶段、报告写入后、未知回执写入后和归档等待五个点，实际杀掉独立 Python worker 进程；原 attempt 不重放，未知回执字节不变。
- 实际创建带本任务所有权标签的 Docker 容器、私有网络和卷，验证恢复清理，并保留一个无关卷。测试发现本机默认地址池耗尽后，使用经冲突检查的独立内部网段，没有清理其他网络或修改 Docker 配置。
- 沿用原有真实执行器超时/取消回归；核验子进程被杀、后续重新核验以及原件篡改后的拒绝也经过实测。

这些是平台回归和受控故障样本，不是缺陷识别准确率、真实模型故障概率或普遍零漏报证明。没有为了通过而调整目标项目或降低断言。

## 3. 历史索引

新增 `acceptance/history.py`，沿用 SQLite WAL。本地文件系统中的两个索引覆盖 native / integration 记录，保存仓库、提交、状态、历史汇总、子执行关系与最近核验时间。索引可丢弃重建；不能写回或替代原件。

生产 HTTP 目录请求只查索引，后台同步运行信封；保存新运行会发出变更标记。同步约每秒检查一次，因此目录是最终一致的历史视图。后台失败保留原索引并显示同步异常。首次建库和重建单独计时，不能冒充热查询性能。

游标以创建时间和唯一 ID 排序，并绑定搜索、仓库及目录类型；同一时间的记录不会重复或遗漏。每页 1–500 条是请求分页大小，不是总量上限。旧接口仍可获取全部条目，前端默认 50 条并支持加载更多和服务器搜索。

列表明确展示“当时判定”。索引里的上次核验时间不等于现在已验证；进入详情或下载核验结果仍校验原件。旧组合运行没有封存完整聚合数时显示“待核对”，不把父执行局部数量冒充完整总数，也不把未知填 0。内部子执行仅按冻结的父子关联隐藏在主目录，证据入口继续保留。

接口：

- `/api/catalogue?kind=records&limit=50&cursor=...&query=...&repository=...`
- `/api/catalogue?kind=repositories&limit=50&query=...`
- `/api/catalogue/records/{id}`：所选历史摘要。

重建命令：`python -m acceptance.history --root var --rebuild`。损坏数据库重建前停止 API 和 worker。旧索引重命名保留；只重建 `history.sqlite3`，不触碰 jobs、运行信封、报告、冻结源码或模型回执。SQLite WAL 目录不能放网络共享盘。

## 4. 重型核验隔离

真实归档并发复核暴露了合成目录基准未覆盖的阻塞：目录请求一度约 22 秒。没有把这次失败删掉。

新增 `acceptance/read_service.py`，使用 Python 标准库进程池执行主详情与结果契约核验，固定最多两个并发核验进程。相同且尚未结束的核验请求复用同一个 future，结束后不缓存为永久有效；再次访问必须重新核验。进程损坏时当前请求失败，新的只读核验可重建 worker。不会由核验进程启动业务执行或调用模型。

进一步将目录同步移到后台，避免 HTTP 列表同步遍历运行信封；历史页面也不再偷偷发起隐藏的完整详情核验。完整大报告仍可能耗时几十秒，不能把首页快等同详情核验瞬时完成。Markdown 大导出等遗留路径未全部迁入独立后台任务，本批不宣称所有读接口均已达成同一时延指标。

随后在真实宿主上仍观测到健康接口 14.66 秒、目录 7.27 秒和浏览器加载超时。读取本机 `launchd.plist(5)` 并检查启动配置，发现 HTTP 服务被设为 `ProcessType=Background`；本机手册明确该类型受资源调度限制。将面向页面的 API 改为 `Interactive`，执行 worker 继续保持 `Background`，未修改其他服务或系统全局配置。同样三份归档并发核验变为 2.450 / 1.950 / 1.681 秒；四次健康查询 2.11–7.54 ms，目录 14.00–32.21 ms，任务列表 5.82–7.12 ms，均 HTTP 200。完整保留调整前、冷启动与调整后样本。该同机对比支持调度配置是此轮重要影响因素，不作为跨机或长期性能保证。

## 5. 任务恢复

沿用 Huey + SQLite，而非新增调度系统。`jobs` 追加 attempt_id、lease_owner、heartbeat_at、recovery_error，旧记录和事件不迁写或删除。实际进程锁是是否可接管的依据，过期时间本身不能抢占仍活着的执行。

生命周期：排队 → 原子领取 attempt → 心跳 → 执行终态。领取使用 CAS，因此重复消息不会重跑已领取任务。队列提交中断由 outbox 重新投递未开始的记录；如果原执行已经开始，恢复保留为 interrupted，必须新建尝试。未领取消息再次丢失可在后续恢复周期重新投递，不要求重启整个 worker。

worker 启动和运行中均进行恢复协调。先清理精确归属本次运行的容器/网络/卷，确认后记录中断；Docker 不可用时保持 recovery_error，其他可处理记录继续。清理失败不会显示为取消或恢复成功。前端显示清理待办及恢复事件链接。

`GET /api/jobs/{id}/events?after=...&limit=...` 提供按事件 ID 分页的审计记录。单次消费者采用排他锁；未来多宿主调度不属于本实现的承诺。

旧未知模型调用不自动重试，也不改成供应方失败。本批没有调用模型。原有 legacy native 配方仍不支持执行中协作取消，接口继续明确拒绝，不能声称所有历史执行器都已支持中途取消。

## 6. 规模基准
