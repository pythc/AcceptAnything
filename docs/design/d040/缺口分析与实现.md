## 本次通用实现

- 文档目录索引：保留全部可识别文档的路径和 SHA；以现有范围文档为主文档，跟随明确的功能链接和 Sphinx toctree 选取补充依据。导航、第三方链接不自动扩张验收范围；未定位锚点有记录。仅映射仓库声明的 Documentation 站点到本地文件，不抓取浮动线上版本、不执行 Sphinx 配置。
- 文档片段：原文连续区间、文档 ID、来源角色、每条链接的选择结果全部冻结。支持大文档分片，无四文件或二十文件的通用方案总量限制；模型接口单次输入预算仍存在，不能承诺任意大小仓库一次请求完成。
- 子项目发现：有明确构建/安装声明的 Python 示例、带 test/build/start 的 Node 子包可成为独立组件；fixtures/testdata/vendor 不自动运行。依赖准备在隔离副本内进行，Node 子包安装祖先声明依赖，Python 本地包绑定冻结源码。
- 服务发现：静态识别直接实例和无必填参数的公开应用工厂；不执行宿主目标代码；服务失败只影响有关验证。
- 合法结果集合：one_of 逐项严格类型比较，空集合拒绝；不把任意返回值视为成功，旧版本不获得新比较权限。
- 缺口分类：basis/environment/platform/case/unclassified。模型分类标明来源；执行异常仅凭可确认的阶段归因，其余待分类。保留原生跳过/错误项的原始说明。

## r1 实测后的增量诊断（尚未代表 r2 完成）

- sqlite-utils 环境校准：Python 3.12.15 / SQLite 3.46.1 / SpatiaLite 5.1.0，按声明编译测试 C 扩展、补充可选 pandas 后，1513 项原生用例全部通过、零跳过；源码快照不变。校准是独立诊断，不代替完整验收记录。
- Flask r1：主包 494 项、JavaScript 示例 8 项、教程示例 24 项原生测试通过，三个示例服务就绪。独立业务用例 2 通过、3 执行异常；不是 3 个产品缺陷。
- 两条引用拒绝：RST 代码块统一展示缩进被模型省略，尚未据此放行。拟增加只允许已定位 RST literal block 的外层缩进定位；原代码内部缩进、空格与字面值必须一致。
- 教程请求 74068524-0f03-4c6c-bb55-cd5c59a7717f 有明确 finish_reason=length，completion_tokens=32768，其中 reasoning_tokens=27680。属于平台分批策略不足，不是“没有需求依据”，不把半截 JSON 当有效方案。
- 业务用例两条猜测 Python 响应存在 `/body`，应调用该对象真实的公开 getter；属于用例观察协议问题。另有两条显式退出指向原上下文管理器，平台只接受 enter 步骤编号，尽管自动兜底已退出。这是可通用兼容的接线问题，且有重入歧义及重复退出的拒绝测试。
- r2 准备方案：保持全部文档目录和选中原文，按限定输出范围分批；每个支持片段作为 focus 一次，其他片段只补充前提，无法纳入上下文的片段明确记账。不是仓库文档总量上限。
- r2 环境准备：解析 GitHub Actions 中原生测试之前的简单依赖和编译声明，拒绝未知条件、任意 shell、覆盖原文件及越界路径。可选导入先探测；安装与验证回执独立留存，部分可选准备失败不能阻止无关检查。

Fastify r1 的四条独立业务用例实际通过：同步响应、异步 JSON、默认 localhost（严格 IPv4/IPv6 候选）、响应 schema 去除额外字段。主 npm test 成功但内层报告为 2378 通过、4 跳过；不能只看退出码。四项经源码核对分别是：一项项目主动跳过的无效 DELETE 请求、两项 Node <24 专属分支（当前 Node >=24，另有对应新版分支）、一项仅 PREPUBLISH 模式启用的生成文件一致性。此为工程核对，不是自动推断；不修改 skip 条件，不启用会重写产物的发布流程换取通过。r2 保留命令级结果及内层汇总、跳过项明细；未知报告格式继续保留原日志，不编造逐项用例。

sqlite-utils r1 的模型请求在发送前因输入体过大被拒绝。不是模型超时，也不是需求缺失。核对发现接口上下文混入大量原生测试函数（仅接口视图已约 454 KB，嵌套后超过请求预算）；r2 将“可调用公共 API”与原生测试目录分开，独立示例组件按自身根目录判断。完整索引仍归档，旧协议回读保留原选择规则。不得把调用 test_* 函数当作模型独立业务验收。

## r2 过程中的分类复核

1. `examples/celery/README.md` 确实给出 `celery -A make_celery worker --loglevel INFO` 和 Web 启动命令。不能笼统说仓库没有启动依据；当前发现结果只收录包声明的命令入口，尚未将文档命令与 broker 配置转为可验证的多服务执行图。因此任务提交/轮询的主要剩余原因是平台编排与环境准备能力，而非文档完全缺失。同步调用加法函数仅验证任务逻辑，不解除这项缺口。
2. 教程初始化数据库在不同批次出现不同判断：B4 将独立 CLI 入口缺失列为缺口，B5 使用公开 `test_cli_runner` 设计了命令和空表读回。须等实际执行后按行为范围核对；命令在进程内通过不证明独立 shell 入口通过。保留两份模型原件，不按标题相同直接删除意见。
3. 部分模型用例直接对普通应用对象执行 `enter`，而非先获取它返回的上下文管理器。这是用例接线问题；驱动不能偷偷补调用某个框架的专用方法让它通过。实际执行回执将保留失败步骤，其他用例继续。

## r2 终态与 r3 复验边界

r2 三份记录均已到终态并完成独立交付核验，目标源码、冻结副本及 Git 状态未变，容器/卷/网络均回收。Flask 35 业务通过、16 异常、3 失败；Fastify 5 业务通过，其原生 npm test 内层为 2378 通过、4 项原生跳过，两个捆绑器命令通过；sqlite-utils 1513 原生通过无跳过、22 业务通过和 1 失败。三份最终结论都是无法完整下结论。

CSV 空单元格的失败有完整命令、输入与读回证据：依据明确写空字符串，但数值列实际为 null。该项保留为文档/行为不一致候选，不能通过改成 null 预期消除。CLI runner 的缺上下文错误和固定 302 猜测则须按用例前提/依据问题处理，不能确认是被测仓库漏洞。

r3 进一步加入独立环境候选、公开字典键读取、实际异常/同一性/路径观察、回调动态字段、成熟 JSON Schema 及字节编码夹具，并对具体状态码和唯一原文引用做确定性校验。所有候选和原始错误保留；业务断言失败不驱动换 Python 或重试。分片仅缩小每次设计负担，所有 focus 仍恰好进入一次任务，未选中的上下文有显式记录。

当前 r3 三仓已使用同一冻结修复版进入完整复验。模型意见即使标题接近也不按语义猜测自动删除；不同批次的需求可能重叠，条目总数变化不能当作覆盖率。本轮最终表需把原生测试、模型设计、业务执行、扫描待复核与尚未覆盖分开报告。
