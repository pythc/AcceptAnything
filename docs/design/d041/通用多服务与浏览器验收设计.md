# D041 通用多服务与浏览器业务验收

本轮延续 Flask、Fastify、sqlite-utils 三个相同提交。执行协议从 17 升为 18。仓库源码、原生测试及依赖声明不因验收通过率而改变。

## 服务发现与编排

从组件自己的源代码/配置字面量识别本地依赖端点，从文档明确的命令识别 worker；保存路径、行号和文件 SHA256。服务依赖图按拓扑顺序启动，逐服务保存实际镜像、命令、启动时间、探针、退出检查和日志。源代码只提供接线信息，不提供业务正确性答案。

复用 Docker 容器生命周期和网络命名空间。依赖服务与当前组件共享隔离网络命名空间，保留源码中的 localhost 地址。数据库和 worker 不向宿主暴露端口；只有中继的 127.0.0.1 临时端口供浏览器访问。原有数据库、宿主账号和生产网络不参与。

首个经实测的组合为 Redis + Celery + Web。Redis 镜像按 ID 锁定，PING 确认就绪；worker 使用文档的应用入口，inspect ping 确认真正在线。solo / concurrency=1 是明确记录的执行资源配置，不使用 eager 或同步函数代替跨进程任务。未支持的连接、认证或服务类型保留环境缺口，不能将某个已注册目录项宣称为已支持服务。

失败只影响依赖节点及声明 requires 的用例。构建、原生测试、扫描及其他独立用例继续。按反向依赖顺序保留日志并清理；异常中断遗留的会话容器也按本次运行标签回收。

## 浏览器协议

新增 journey 用例。setup / cleanup 复用原有的公开 API 声明协议，app 引用准备过程中返回的真实应用对象。Python 复用 Werkzeug / Uvicorn，Node 使用应用的公开 listen 方法。每条用例独立进程、临时目录、数据和浏览器 context，不使用原生测试残留的数据。准备阶段异常、CLI 非零退出、缺少最终清理回执都属于执行异常。

复用 Playwright 真实 Chromium 的定位器、自动等待和断言。支持打开页面、表单填写、点击、键盘、选择、勾选、原生确认框，以及页面文本、地址、值、属性、元素数量、可见性、原生表单校验。request / poll 使用同源 HTTP，可提交表单或 JSON，按独立预期等待结果；捕获结果只用于后续动作输入，不作为预期答案。等待预算不是性能 SLO。

只向目标应用传入准备动作和输入。业务断言由可信 Playwright 驱动执行。用例可使用模板属性选择定位器，但正确结果只能来自独立文档。无 Web 应用声明的 CLI 项目继续使用 CLI / scenario，不强造浏览器通过项。

每一步保留原始动作、实际观察、预期、状态、耗时和截图；整条用例保留 trace、完整 HAR、浏览器事件、应用日志、准备与清理回执。动作或驱动异常是 error，独立断言不符是 failed，都不自动变成已确认产品缺陷。完整性复核核对冻结步骤、实际执行顺序、浏览器原件与会话清理。

## 验证安排

先使用中立夹具验证契约拒绝、真实表单与异步轮询、断言失败及动作失败证据，再用冻结项目做协议校准。校准输入是诊断资料，不是平台中的项目专用配方，也不计入整轮模型验收通过数。

随后冻结本轮执行代码，用官方 DeepSeek Flash / High 重新设计中文用例，按普通入口完整重跑三个仓库。模型原件、失败、缺口及未知状态全部保留。只有完整执行和完整性有效，仍不足以证明验收通过；覆盖缺口继续参与门禁。
